## Services

### AllocationService

AllocationService is the read-only half of the engine: it answers how much is free, and never changes anything. HoldService is the half that takes.  The counting is done here rather than stored anywhere. No RFC models an inventory count -- RFC 5545 and RFC 7953 are one-calendar-one-timeline -- so "5 of 12 free" is produced by asking each RFC 9073 resource's calendar whether it is free across the window and totalling the answers. RFC 7953's VAVAILABILITY says when a resource was on offer at all; bookings on its calendar say what has since been taken; the difference is availability.  Every operation is a custom method (AIP-136): they compute rather than fetch, so they take neither the standard-method names nor their shapes.

| Method | Request | Response | Description |
| --- | --- | --- | --- |
| `ComputeAvailability` | `ComputeAvailabilityRequest` | `ComputeAvailabilityResponse` | Computes availability across a site's resources, bucketed by slot or day. |
| `CheckAvailability` | `CheckAvailabilityRequest` | `CheckAvailabilityResponse` | Checks one exact window for one exact quantity, with reasons when it fails.  Advisory, not a reservation: the answer can be stale the instant it is returned. CreateHold is what actually secures anything. |
| `BatchComputeAvailability` | `BatchComputeAvailabilityRequest` | `BatchComputeAvailabilityResponse` | Runs several availability computations in one round trip.  Each entry is independent and may name a different site, window or granularity. Capped at 50 entries, because each one fans out across every candidate resource's calendar. |
| `SearchAvailability` | `SearchAvailabilityRequest` | `SearchAvailabilityResponse` | Sweeps an operator for resources free across a window.  The search entry point, where ComputeAvailability answers for a site the caller has already chosen. Paginated, since a large operator may match thousands of resources. |

### HoldService

HoldService takes and releases expiring claims on resources. It is the only thing in this API that mutates availability.  Two things are deliberately not RPCs: the sweeper that expires lapsed holds is an internal job, not a call, and conversion to a confirmed booking is driven by ReservationService, so a hold is never converted by a caller reaching in here.  There is no UpdateHold. A hold's window and resources are immutable by construction -- changing either is a different allocation -- so the only mutations are the two custom methods below.

| Method | Request | Response | Description |
| --- | --- | --- | --- |
| `CreateHold` | `CreateHoldRequest` | `Hold` | Takes a hold, allocating concrete resources for the window.  The server chooses which resources are taken from the candidates offered, under a lock, so two callers racing for the last bay cannot both win. Requires an idempotency key: a retry after a timeout returns the original hold rather than taking a second one. |
| `GetHold` | `GetHoldRequest` | `Hold` | Retrieves one hold.  Authoritative on expiry: a hold whose expire_time has passed is reported EXPIRED here even if the sweeper has not yet written that state, so a caller never sees an ACTIVE hold that no longer reserves anything. |
| `ListHolds` | `ListHoldsRequest` | `ListHoldsResponse` | Lists the holds taken at a site. |
| `ExtendHold` | `ExtendHoldRequest` | `Hold` | Pushes a hold's expiry further out.  Measured from now rather than from the current deadline, so repeated calls cannot accumulate an unbounded reservation. Fails on a hold that is not ACTIVE -- an expired hold is gone, not extendable. |
| `ReleaseHold` | `ReleaseHoldRequest` | `Hold` | Gives a hold up before it expires, freeing its resources immediately.  Idempotent: releasing an already-released or expired hold succeeds and changes nothing, because the caller's intent is already satisfied. |

## Messages

### Hold

A Hold is a temporary, expiring claim on one or more bookable resources for a window, taken before payment or confirmation so two callers cannot be sold the same thing.  Native, with no RFC behind it, and the comment says why (the same trade protobuf.shared.project.v1 records upstream). RFC 5545 section 3.2.12's PARTSTAT=TENTATIVE can express that a claim is provisional, and RFC 5546's iTIP can carry the request that created it, but neither specifies a lapse time, and an expiring claim is the one thing a commercial booking engine cannot do without. The resources held are RFC 9073 VRESOURCEs and the window is measured against their RFC 7953 availability; only the clock is ours.  Holds are allocated, not requested: CreateHold names candidate resources and a quantity, and the server decides which concrete resources are taken. That keeps "which bay did I get" a server decision made under a lock, rather than a client guess that races.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `name` | `string` | `IDENTIFIER` | The hold name. Nested under the site whose resources it takes, so a hold is listed and swept per site without joining through every resource. Format: organizationalUnits/{organizational_unit}/holds/{hold} |
| `resources` | `repeated string` | `OUTPUT_ONLY` | The concrete resources this hold has taken, one per unit of `quantity`. Chosen by the server from the candidates the request offered. Format: resources/{resource} |
| `window` | `Interval` | `REQUIRED` | The window held. Immutable: moving it is a different allocation, so release this hold and take another. |
| `candidate_resources` | `repeated string` | `OPTIONAL` | Candidate resources the allocator may choose from, supplied on create. Empty offers every resource the site holds. Immutable: the choice is made once, and re-offering a different set is a different allocation. Format: resources/{resource} |
| `quantity` | `int32` | `OPTIONAL` | How many resources to take, supplied on create; defaults to 1. Once the hold is ACTIVE this equals the length of `resources`. |

### Allocation

An Allocation is one resource taken by one hold for one span: the row the engine counts when it asks what is already claimed.  Storage-only. No RPC returns it -- callers see a Hold and its `resources` -- but a Hold cannot answer "who has bay 14 at 10:00" on its own: its window is one value and its resources a list, so an overlap query over holds would have to unpack both on every row. One row per resource, with the span as two indexed instants, makes that query a plain range scan on either backend.  The span and `expire_time` are copies of the hold's, written in the same write as the hold. The copy is the point: a claim stops counting the instant `expire_time` passes, with no sweeper write needed, because every read filters on it.  It sits under the site and names its hold, rather than nesting under the hold: the engine asks about allocations by resource and time across a whole site, never hold by hold, and a hold with child resources would owe DeleteHold a `force` flag guarding rows no caller can see.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `name` | `string` | `IDENTIFIER` | The allocation name, under the site whose resource it takes. Format: organizationalUnits/{organizational_unit}/allocations/{allocation} |
| `resource` | `string` | `REQUIRED` | The resource taken. Format: resources/{resource} |
| `start_time` | `Timestamp` | `REQUIRED` | Start of the span taken, inclusive. A copy of the hold's window start. |
| `end_time` | `Timestamp` | `REQUIRED` | End of the span taken, exclusive. A copy of the hold's window end. |
| `expire_time` | `Timestamp` | `OUTPUT_ONLY` | When this claim stops counting. A copy of the hold's expire_time while it is ACTIVE; set to the release instant on release; unset once the hold is CONVERTED, which is the one outcome that keeps the resource taken. Always the server's to write, never a caller's. |

## Enums

### HoldState

Lifecycle of a Hold. A hold is the only thing in this API that expires on its own: RFC 5545 section 3.2.12's PARTSTAT=TENTATIVE says a tentative claim exists, but no RFC says when it lapses, so the clock is ours.

| Value | Number | Description |
| --- | --- | --- |
| `HOLD_STATE_UNSPECIFIED` | 0 | Default; never persisted. |
| `HOLD_STATE_ACTIVE` | 1 | Live and holding its resources against other callers, until expire_time. |
| `HOLD_STATE_RELEASED` | 2 | Given up before expiry, by ReleaseHold or by the booking it backed failing. The resources are free again. |
| `HOLD_STATE_EXPIRED` | 3 | expire_time passed with no confirmation. Reached by the sweeper, and by any authoritative read that notices the deadline before the sweeper does, so a stale ACTIVE row never hands out a resource twice. |
| `HOLD_STATE_CONVERTED` | 4 | Converted into a confirmed booking. Terminal, and the only outcome that keeps the resources allocated. |
